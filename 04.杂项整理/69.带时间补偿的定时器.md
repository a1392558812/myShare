# 带时间补偿的定时器

> 核心思路：不用「定时器被触发了几次」来计数，而是每次触发时用真实时间反推「到现在为止本该执行几次」，再补上差量。页面阻塞（主线程卡顿、标签页挂起）不会导致少执行，长期运行也不会漂移。

## 适用场景

- **次数敏感**（心跳上报、按次累加、采样计数）：保留默认 `compensate: true`，阻塞恢复后补齐漏掉的次数。
- **只关心最新状态**（刷新 UI、节流渲染）：建议 `compensate: false`，补偿执行反而没有意义，还会造成同一时刻连续渲染。
- **回调是异步的**（请求、IO）：hook 只负责同步调用，返回值被忽略；补偿批次会同步连发多次，**防并发、取消由使用者自行处理**。

## 抬杠环节

假设 `step = 1000`，t=0 `start`，正常跑到t=3000，然后页面阻塞到t=13000 恢复。正常阶段：t=1000/2000/3000各tick 一次，`executedCount` 走到3。t=13000 恢复：`tickTime = 13000`，`expected = 13`，`pending = 13 - 3 = 10`。

### 情况 A：`compensate: true`，`maxCatchUp: 1000`（不截断）

`dropped = 0`，`total = 10`，循环 10 次：

| 第几次 | `executedCount` | `ctx.count` | `ctx.expected` | `ctx.lastExecTime` | `ctx.execTime - lastExecTime` |
| ------ | --------------- | ----------- | -------------- | ------------------ | ----------------------------- |
| 1      | 4               | 4           | 13             | 3000               | **10000**（真实阻塞时长）     |
| 2      | 5               | 5           | 13             | 13000              | 0                             |
| …      | …               | …           | …              | …                  | 0                             |
| 10     | 13              | 13          | 13             | 13000              | 0                             |

tick 结束时 `executedCount = 13 = expected`。

> `ctx` 在 `invoke` 更新 `lastExecTime` 之前构造，所以第 1 次读到的是上次执行时刻3000；执行后`lastExecTime`变成 13000，第2次读到13000，`execTime - lastExecTime = 0`。

**回调内前 9 次 `count < expected` 成立**，最后一次相等。这说明：`count < expected` 在补偿批次里是**常态**，它描述的是「批次进度」，不是「有没有丢过次数」。

### 情况 B：`compensate: true`，`maxCatchUp: 5`（截断）

`pending = 10 > 5` → `dropped = 5`，`executedCount += 5` 变成 8，`pending = 5`，`total = 5`：

| 第几次 | `executedCount` | `ctx.count` | `ctx.expected` | `ctx.dropped` |
| ------ | --------------- | ----------- | -------------- | ------------- |
| 1      | 9               | 9           | 13             | 5             |
| …      | …               | …           | …              | 5             |
| 5      | 13              | 13          | 13             | 5             |

tick 结束时同样 `executedCount = 13 = expected`。

截断时 `executedCount` 先预加了 `dropped`，所以**批次跑完依然能追平 `expected`**。区分 A 和 B 的唯一可靠信号是 `dropped > 0`，不是 `count < expected`。

### 情况 C：`compensate: false`

```ts
const skipped = pending - 1   // 10 - 1 = 9
executedCount = expected      // 直接跳到 13
invoke(...)                   // ctx.count = 13, ctx.expected = 13, ctx.dropped = 9
```

回调只调一次，`count === expected` 恒成立，`count < expected` 永远为 `false`。丢没丢只能看 `dropped = 9`。

> 注意：`count` 会**跳跃**（3 → 13），不要用它统计「实际调用了几次」，也不要用 `count >= N` 做停止条件（可能直接跳过 N）。要统计实际调用次数，自己在回调里累加。

## 如何判断「丢过次数」

按可靠性排序：

1. **`dropped > 0`**：本 tick 明确有欠账被丢弃。`compensate: false` 时是 `pending - 1`，`compensate: true` 截断时是超 `maxCatchUp` 的部分。语义最直接。
2. **`isCatchUp === true`**：本 tick 正在补执行（`catchUpTotal > 1`），说明之前丢过。批次内第一次的 `execTime - lastExecTime` 就是真实阻塞时长。
3. **`execTime - lastExecTime > step * 1.5`**：跨 tick 看真实间隔，理论上至少该执行 2 次，说明中间丢过。与 `compensate` 无关，两种模式都成立；批次内后续几次 `execTime - lastExecTime === 0`，不会重复触发。

// 补充：关于第 3 条的 `1.5`：

- 它是**容差系数**，不是精确判据。正常 tick 的 `execTime - lastExecTime` 几乎不会精确等于 `step`，总是略大（计时精度 + 调度延迟），所以阈值要大于 `step`，把抖动包进去。
- 丢 1 次时真实间隔约 `2 * step`，丢 2 次约 `3 * step`，所以阈值落在 `(1, 2) * step` 之间都能区分「没丢」和「至少丢 1 次」。`1.5` 取中间，容差 50%，可改成 `1.2`（更敏感，`step` 小时易误报）或 `1.8`（更保守）。
- **在已有 `dropped` / `isCatchUp` 的前提下，这条基本冗余**：补偿批次第一次 `isCatchUp` 已为 `true`，截断时 `dropped > 0`。它只在想做跨tick的自定义监控时才需要，且`step` 很小时（如 16ms）抖动占比变大，不要依赖它。

```ts
useStepInterval(1000, ({ execTime, lastExecTime, step, dropped }) => {
  // 最直接：本次 tick 有欠账被丢弃
  if (dropped > 0) console.warn(`丢弃 ${dropped} 次`);

  // 跨 tick 看真实间隔，两种模式通用（可选）
  const realStep = execTime - lastExecTime;
  if (realStep > step * 1.5) {
    console.warn(
      `距上次 ${realStep.toFixed(0)}ms，期间本应多执行 ${Math.floor(realStep / step) - 1} 次`,
    );
  }
});
```

**`count < expected` 描述「批次进度」，`dropped` / `isCatchUp` / `execTime - lastExecTime` 才是「是否丢过次数」的判据。**

## 完整代码

```ts
// useStepInterval.ts
import { onBeforeUnmount, getCurrentInstance, ref } from "vue";
import type { Ref } from "vue";

export interface StepIntervalOptions {
  /**
   * 是否补偿因页面阻塞而漏掉的执行次数
   * - true（默认）：按真实时间对齐，补齐漏掉的次数
   * - false：每次触发只执行一次，丢弃漏掉的次数
   *          （仍按真实时间对齐，长期不漂移；executedCount 直接对齐到 expected）
   */
  compensate?: boolean;

  /**
   * compensate 为 true 时，单次 tick 最多补执行多少次，防止长时间阻塞后
   * 一次性补执行过多把页面再卡死。默认 1000。
   *
   * 注意：
   * - 传 Infinity 表示严格补全所有欠账。页面挂起 20 分钟、step = 1000 时
   *   就是 1200 次同步补执行，可能再次卡死页面，除非明确需要，否则不要用。
   * - 应传正数或 Infinity；传负数会导致 dropped 计算异常、全部丢弃（未定义行为）。
   */
  maxCatchUp?: number;

  /**
   * 是否 start 时立即先执行一次（这次不计入节拍对齐）
   * immediate 那次回调里 count = 0、expected = 0。
   */
  immediate?: boolean;
}

/**
 * 回调上下文
 *
 * - 真实间隔 = execTime - lastExecTime
 * - 已流逝时长 = execTime - startTime
 */
export interface StepIntervalContext {
  /** 停止函数。回调内调用会立即终止后续调度与本次未完成的补执行。 */
  stop: () => void;

  /** 配置的步长（ms）。 */
  step: number;

  /** 会话号，每次 start 自增。用于识别回调是否来自同一轮（stop 后 start 会变）。 */
  session: number;

  /**
   * 节拍计数（1-based）。immediate 立即执行的那次为 0（不计入节拍）。
   *
   * compensate: false 时它会对齐到理论值、会跳跃（如 3 → 13），
   * 不代表实际调用次数。不要用 count 统计调用次数，也不要用 count >= N 做停止条件
   * （可能直接跳过 N）。要统计实际调用次数，请在回调里自行累加。
   */
  count: number;

  /** 本轮 start 的时刻。start 后固定不变，用于节拍对齐。 */
  startTime: number;

  /**
   * 上一次执行的时刻；本轮首次执行时等于 startTime。
   *
   * 注意：ctx 在 invoke 更新 lastExecTime 之前构造，所以补偿批次中
   * 第 1 次读到的是上次执行时刻，第 2 次起读到的是本批 tickTime，
   * 因此「批次内除首次外 execTime - lastExecTime ≈ 0」。
   */
  lastExecTime: number;

  /** 本次执行的时刻；同批补执行共享同一 tick 时刻。 */
  execTime: number;

  /** 到此刻理论上应执行的总次数（整批补执行共享同一个值）。 */
  expected: number;

  /** 本次是否处于补偿批次（catchUpTotal > 1 时为 true）。 */
  isCatchUp: boolean;

  /** 本次补偿批次中的序号（1-based）；非补偿时为 1。 */
  catchUpIndex: number;

  /** 本次补偿批次的总次数；非补偿时为 1。 */
  catchUpTotal: number;

  /**
   * 本次 tick 中被丢弃、未执行的理论次数
   * - compensate: true：因超过 maxCatchUp 被丢弃的次数
   * - compensate: false：本次欠账中除实际执行的 1 次外，全部丢弃的次数（pending - 1）
   *
   * 这是判断「是否丢过次数」最可靠的信号（dropped > 0）。
   */
  dropped: number;
}

export type StepIntervalCallback = (ctx: StepIntervalContext) => void;

export interface StepIntervalController {
  /** 启动。已在运行时幂等返回。会重置 session / startTime / lastExecTime / executedCount。 */
  start: () => void;
  /** 停止。清除定时器 */
  stop: () => void;
  /** 是否运行中。 */
  isRunning: Ref<boolean>;
}

const now = (): number =>
  typeof performance !== "undefined" ? performance.now() : Date.now();

/**
 * 按真实时间对齐的 setInterval。
 * callback 按同步调用处理：返回值被忽略，异步逻辑（含取消、防并发）由使用者自行管理。
 *
 * 组件外使用时不会自动清理（getCurrentInstance() 为 null），必须手动 stop，否则定时器泄漏。
 */
export const useStepInterval = (
  step: number,
  callback: StepIntervalCallback,
  options: StepIntervalOptions = {},
): StepIntervalController => {
  if (!Number.isFinite(step) || step <= 0) {
    throw new RangeError("[useStepInterval] step 必须是大于 0 的有限数字");
  }

  const { compensate = true, maxCatchUp = 1000, immediate = false } = options;

  let timer: ReturnType<typeof setTimeout> | null = null;
  const running = ref(false);
  /** 会话号：识别「同一轮调度」，stop 后立刻 start 时旧批次会立即退出，不会串台 */
  let session = 0;
  /** 本轮 start 时刻，固定不变，节拍始终锚定在 startTime + n * step 上 */
  let startTime = 0;
  /** 上一次执行时刻，初始化为 startTime */
  let lastExecTime = 0;
  /** 累计已认定的节拍数（即回调里的 count） */
  let executedCount = 0;

  const clearTimer = (): void => {
    if (timer !== null) {
      clearTimeout(timer);
      timer = null;
    }
  };

  const stop = (): void => {
    running.value = false;
    clearTimer();
  };

  const makeCtx = (
    execTime: number,
    expected: number,
    isCatchUp: boolean,
    catchUpIndex: number,
    catchUpTotal: number,
    dropped: number,
  ): StepIntervalContext => ({
    stop,
    step,
    session,
    count: executedCount,
    startTime,
    lastExecTime,
    execTime,
    expected,
    isCatchUp,
    catchUpIndex,
    catchUpTotal,
    dropped,
  });

  const invoke = (ctx: StepIntervalContext): void => {
    // 先更新 lastExecTime，再回调：保证下一批 ctx.lastExecTime 是本次执行时刻
    lastExecTime = ctx.execTime;
    try {
      callback(ctx);
    } catch (err) {
      console.error("[useStepInterval] callback 执行出错:", err);
    }
  };

  /**
   * 按「理论时间点」安排下一次触发，而非固定 setTimeout(step)。
   * 这样回调自身耗时、定时器精度误差都不会累积成漂移。
   */
  const schedule = (): void => {
    const nextTime = startTime + (executedCount + 1) * step;
    const delay = Math.max(1, Math.ceil(nextTime - now()));
    timer = setTimeout(tick, delay);
  };

  const tick = (): void => {
    timer = null;
    if (!running.value) {
      return;
    }

    const currentSession = session;
    const tickTime = now();
    // 核心：用真实流逝时间反推「到此刻理应执行了几次」
    // +1e-6 用于消除浮点误差（如 2.9999999999999996 被 floor 成 2）
    const expected = Math.floor((tickTime - startTime) / step + 1e-6);
    let pending = expected - executedCount;

    if (pending <= 0) {
      // 定时器因精度问题提前一点点触发：expected === executedCount
      // 不执行回调，直接重排下一次
      if (running.value && session === currentSession) {
        schedule();
      }
      return;
    }

    // 分支一：不补偿。丢弃欠账，只执行一次，executedCount 直接对齐到 expected
    // 必须对齐，否则下次 tick 仍会算出一大截欠账，导致连续触发
    if (!compensate) {
      const skipped = pending - 1;
      executedCount = expected;
      invoke(makeCtx(tickTime, expected, false, 1, 1, skipped));
      if (running.value && session === currentSession) {
        schedule();
      }
      return;
    }

    // 分支二：补偿。超过上限的部分直接丢弃，避免「补执行」再把页面卡死
    // 先预加 dropped，保证批次跑完仍能追平 expected
    let dropped = 0;
    if (pending > maxCatchUp) {
      dropped = pending - maxCatchUp;
      executedCount += dropped;
      pending = maxCatchUp;
      console.warn(`[useStepInterval] 阻塞过久，已丢弃 ${dropped} 次补执行`);
    }

    // 同步补齐漏掉的次数；callback 里 stop 或 restart 都能让循环及时退出
    const total = pending;
    let index = 0;
    while (pending-- > 0) {
      if (!running.value || session !== currentSession) {
        return;
      }
      executedCount++;
      index++;
      // 同批补执行共用 tickTime：批次内除首次外 execTime - lastExecTime ≈ 0
      invoke(makeCtx(tickTime, expected, total > 1, index, total, dropped));
    }

    if (running.value && session === currentSession) {
      schedule();
    }
  };

  const start = (): void => {
    if (running.value) {
      return;
    }
    running.value = true;
    session++;
    startTime = now();
    lastExecTime = startTime;
    executedCount = 0;

    if (immediate) {
      // count = 0 表示这次是不计入节拍对齐的额外执行
      invoke(makeCtx(now(), 0, false, 1, 1, 0));
      if (!running.value) {
        return;
      }
    }
    schedule();
  };

  // 组件内自动清理；组件外调用不会报错（但需要使用者手动 stop）
  if (getCurrentInstance()) {
    onBeforeUnmount(stop);
  }

  return { start, stop, isRunning: running };
};
```

## 示例

```html
<template>
  <div>{{ dateTime }} / {{ testCount }} / {{ isRunning }}</div>
  <button @click="stop">停止</button>
  <button @click="start">开始</button>
</template>

<script setup lang="ts">
  import { ref } from "vue";
  import { useStepInterval } from "@/hooks/useStepInterval";

  const testCount = ref(0);
  const dateTime = ref(new Date());

  // 默认开启补偿：页面卡顿后会把漏掉的次数补回来
  const heartbeat = useStepInterval(1000, ({ dropped, isCatchUp }) => {
    testCount.value++;
    dateTime.value = new Date();
    if (dropped > 0) console.warn(`丢弃 ${dropped} 次`);
    if (isCatchUp) console.info("本次为补偿批次");
  });

  const { isRunning, start, stop } = heartbeat;

  // 关闭补偿：只关心「现在有一次 tick」，漏掉的不补
  const sampler = useStepInterval(
    100,
    () => {
      // 只做一次采样/刷新
    },
    { compensate: false },
  );
  sampler.start();
</script>
```
