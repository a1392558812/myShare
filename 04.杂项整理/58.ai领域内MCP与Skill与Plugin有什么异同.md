# ai领域内MCP与Skill与Plugin有什么异同

> 这三老被人摆一块，其实不在一个层次上，不存在谁替代谁。**MCP 管「连不连得上」，Skill 管「会不会干」，Plugin 管「怎么打包发给别人」**。

---

## MCP：给 AI 装的「标准接口」

> MCP（Model Context Protocol）是 2024 年 11 月 Anthropic 开源的开放协议，专门解决 LLM 应用和外部数据源、工具之间的连接问题。底层走 JSON-RPC 2.0。

### Host → Client → Server

| 角色 | 做什么 | 说明 |
| :--- | :--- | :--- |
| **MCP Host** | AI 应用本体 | Claude Code、VS Code 这类，负责协调底下的一堆连接 |
| **MCP Client** | 连接实例 | Host 每接一个 Server 就开一个，一一对应，各管各的 |
| **MCP Server** | 提供数据 / 能力的程序 | 本地跑走 STDIO，远程跑走 Streamable HTTP |

举个栗子：VS Code 作为 Host，连 Sentry 的 MCP Server 时会实例化一个 Client 专门伺候这条连接；回头再连本地文件系统 Server，就再开一个 Client。彼此独立，一条断了不至于全崩。

### 协议就两层

| 层次 | 职责 |
| :--- | :--- |
| **数据层（Data Layer）** | JSON-RPC 的通信约定：能力协商、版本发现，以及四个核心原语 Tools / Resources / Prompts / Notifications |
| **传输层（Transport Layer）** | 具体怎么传：STDIO、Streamable HTTP 等 |

### 2026 年这次改版：把「状态」砍了

2026 年 7 月 28 日，Anthropic 发了第五版规范，官方自己的定性是"自协议问世以来规模最大、最系统性的一次颠覆式修订"。

核心变化一句话：**从有状态（Stateful）全面转向无状态（Stateless）**。

- 初始化握手和 `Mcp-Session-Id` 直接删掉，每个请求自己带上协议版本和能力信息，自包含。
- 好处是 Server 可以往 AWS Lambda、Cloudflare Workers 这类 Serverless 上丢，请求爱打给哪个实例就打给哪个，横向扩容不用再粘会话。
- 以前"一个 Pod 重启或崩了，会话状态立马丢失，直接给活跃中的客户端抛瞬态错误"——无状态化之后这类幺蛾子从根上没了。

### 安全这块有个坑：工具投毒

MCP 在表面没问题，客户端 / 宿主 / 服务器三层边界清清楚楚。实操里有个问题是 **「工具投毒」（Tool Poisoning）**：

攻击者不动你一行代码，专挑工具元数据的 `description`、参数 schema 这些字段塞恶意指令。但 LLM 把这些指令统统当"权威说明"，还特别听话地照做。工具本身干干净净，坏的是那份说明书。

OWASP 把根因概括为"连接时信任与运行时之间的信任鸿沟"。新规范加了 `server/discover` RPC、强化了 OAuth 2.0 / OIDC 来补，但这还属于"建立信任"层面的活儿；正儿八经的防止工具投毒，还是得在运行时对工具元数据做动态审查。

### 什么时候用它

MCP 管的是 **「AI 能不能连上」**。查数据库、调 API、控浏览器、读写文件这类要碰外部系统的场景，写个 MCP Server 就是标准接法。

## Skill：给 AI 塞一本「岗位手册」

> Skill 是 Anthropic 2025 年 12 月发布的 Agent Skills 开放标准。说穿了就是**一组结构化的提示词**，把能复用的工作流和领域知识打包成 AI 会自动发现、按需加载的模块。

### 一个 Skill 就是一个文件夹

```
skill-name/
├── SKILL.md          # 必须有：元数据 + 指令正文
├── scripts/          # 可选：能跑的脚本
├── references/       # 可选：参考文档
├── assets/           # 可选：模板、资源文件
└── ...               # 想塞啥塞啥
```

### SKILL.md 怎么写

头部 YAML frontmatter，下面 Markdown 正文，各写各的：

| 字段 | 必填 | 约束 |
| :--- | :--- | :--- |
| `name` | 是 | 最长 64 字符，只能小写字母、数字、连字符，不能以连字符开头或结尾 |
| `description` | 是 | 最长 1024 字符，要说清"做什么"和"什么时候用" |
| `license` | 否 | 许可证名字，或者指到包里的许可证文件 |
| `compatibility` | 否 | 最长 500 字符，说环境要求（目标产品、系统包、要不要联网等） |
| `metadata` | 否 | 任意键值对，随便挂 |
| `allowed-tools` | 否 | 预先放行的工具列表（实验性） |

一个典型的长这样：

```yaml
name: pdf-processing
description: Extract PDF text, fill forms, merge files. Use when handling PDFs.
license: Apache-2.0
metadata:
  author: example-org
  version: "1.0"
```

### 三层渐进式披露：用多少拿多少

Skill 最巧的设计叫 **「渐进式披露」（Progressive Disclosure）**，信息分三层按需喂进来，主打一个不撑爆上下文：

| 层级 | 什么时候加载 | 加载什么 | 上下文开销 |
| :--- | :--- | :--- | :--- |
| **Level 1** | Agent 启动就加载 | `name` + `description` 进系统提示 | 几十个 token |
| **Level 2** | Agent 判断任务对得上时 | 完整的 `SKILL.md` 正文 | 目标 < 5k token，硬顶 64 KiB |
| **Level 3** | Agent 需要时拿 Read / Bash 去读 | `references/`、`scripts/`、`assets/` 里的东西 | 按需，用多少算多少 |

`SKILL.md` 正文硬上限 64 KiB，Anthropic 官方最大的那个 skill-creator 也就 32 KiB 上下，余量大得很。

### 到底是社么

// Skill **本质就是结构化的提示词**，跟深度学习那套知识蒸馏半毛钱关系没有。不改模型参数，也不凭空捏造推理能力，只是在模型上面又糊了一层可复用的任务指令。

打个比方：大模型是个啥都懂一点、啥都不精通的应届通才，Skill 就是你递过去的一本岗位手册。手册写得再厚，通才还是那个通才——只是这回他知道按你的规矩干活了。

### 什么时候用它

Skill 管的是 **「AI 知不知道该怎么干」**。要它按特定规范写文档、跑多步骤工作流、守公司的品牌指南，用 Skill 装就对了。

## Plugin：把前面那俩打包成「安装包」

> Plugin 是 **Agent Plugins 1.0.0** 规范定义的打包格式，OpenAI 拉着 AWS、Cursor、微软、Vercel 在 2026 年 8 月发布，后来 Google 也进了核心维护。目的很单纯：**打一次包，所有兼容的 Agent 客户端都能装**。

### 目录结构，短得离谱

```
reports-plugin/
├── plugin.json          # 清单文件（必需）
├── skills/              # Agent Skills（可选）
│   └── summarize/
│       ├── SKILL.md
│       ├── scripts/
│       └── references/
├── mcp.json             # MCP 服务器配置（可选）
└── com.example.client/  # 客户端专属扩展（可选）
```

清单文件也就两个字段必填：

```json
{
  "$schema": "https://agent-plugins.org/schemas/1.0.0/plugin.schema.json",
  "name": "reports-plugin"
}
```

位置全是定死的：Skill 一律扔 `skills/` 下，一个子目录一个，照 Agent Skills 规范来；MCP Server 在 `mcp.json` 里声明，每条还得明写传输类型——不让客户端对着配置对象瞎猜。

### 这个规范很好的一点：少管闲事

`plugin.json` 从头到尾贯彻「能不管就不管」：

- 不能重新指定组件位置，不能内联声明组件，没有要配的发现路径，也没有要背的优先级顺序。
- `skills/` 目录不存在？那就加载有东西的那部分，接着往下走。
- 某个 MCP Server 起不来？不拖累 Skills，客户端跳过这一条、记一笔失败，继续加载。

一句话：**别让一个坏组件把整个包带沟里**。

### 各家自己的私货往哪塞

Hooks、斜杠命令、自定义界面这类客户端特有的玩意儿，丢到**反向域名命名**的目录里就行（比如 `com.example.client/`）。别的客户端扫到不认识，直接略过，公共层始终干干净净。

### 现在到哪一步了

Agent Plugins 1.0.0 目前还挂着 **「工作草案（Working Draft）」** 的牌子，并不是行业标准。不过 Cursor、GitHub、Microsoft、Google 这些主要玩家都已经站队宣布支持了。依葫芦画瓢，咱也跟着这个规范来，

### 什么时候用它

Plugin 管的是 **「这套能力怎么发给团队」**。当你手上一堆 Skill + MCP 配置要跨平台跨客户端复用，不想给每个客户端重新打包一遍的时候，就该它出场了。

## 一套四层能力栈

| 层级 | 概念 | 类比 | 解决了啥 |
| :--- | :--- | :--- | :--- |
| **分发层** | Plugin | 应用安装包 | 能力怎么打包、分发、跨平台安装 |
| **知识层** | Skill | 岗位手册 / SOP | AI 知不知道怎么干某件事 |
| **集成层** | MCP | USB-C 接口 | AI 能不能连上外部系统 |
| **执行层** | Tool | 具体动作 | AI 能不能真的去做某个操作 |

**协作逻辑其实就一句话**：开发者写好 Skill（操作手册）+ MCP Server 配置（连接线），一块塞进 Plugin（安装包）。用户装上之后，AI 同时拿到"知道怎么干"和"能够连外系统"两样东西。

举个实际点的例子：一个"查数据库、写周报"的 Plugin 就两块——**Skill** 教 AI 把查询结果整理成团队爱看的周报格式，**MCP Server** 负责替 AI 连上库。搁以前，想让它在 Cursor、GitHub Copilot、Codex 里都能用，得打三份包、改一处改三遍；现在打一份、改一遍就完事。

> **一点建议**：80% 的场景下 **「Skill + MCP」 这俩组合已经够用了**。Plugin 真正发光是在规模上来之后，解决团队协作和能力分发那摊事。
