# 从零写一个最小可用 Skill

> 本文为水字数炒冷饭文章，之前好像写过，懒得检查了，这章可看可不看

`SKILL.md` 里写清楚两件事：

1. **什么场景触发它**：YAML 元数据头里的 `description`（Agent 判定是否启用的唯一依据）
2. **触发后按什么步骤干活、产出达到什么标准**：正文（核心指令、工作流、审查规范、交付格式）

| 前端概念                  | 对应到 Skill                                 |
| ------------------------- | -------------------------------------------- |
| 函数封装                  | 把"反复解释团队规范"的重复劳动封装成固定流程 |
| npm 包 / 脚手架           | 一个自带文档、模板、工具脚本的分发单元       |
| ESLint 规则命中           | `description` 决定"什么时候触发这个 Skill"   |
| props 契约（I/O 接口）    | 用户需求（输入）→ 符合规范的产物（输出）     |
| 按需加载 / code splitting | 渐进式披露：触发才加载正文，需要才读资源     |

---

## 为什么要写 Skill

eg:你在团队里用AI 辅助写Vue3组件。没有Skill 时，每次都要重新解释一遍："用 TypeScript，`<script setup>`，props 用 camelCase，样式 scoped，组件放 `src/components/<名字>/`，再加 `index.ts` 统一导出……"

说一次两次还行，说十次就烦了；而且每次 Agent 的理解还不一致，输出时好时坏。

Skill 解决的是：把"你希望 Agent怎么干活"变成一份固定、可复用的说明书。之后你只需要说一句"写个带防抖的搜索框组件"，Agent会自己读取这份说明书，按你的规范一次到位。

## 是什么

一个 Skill 就是一个普通文件夹，不涉及任何特殊格式：

```
vue3-sfc-generator/
├── SKILL.md          # 必需：说明"何时用 + 怎么用"
├── scripts/          # 可选：可执行的确定性脚本（如代码生成器）
├── references/       # 可选：需要时再加载的参考资料（如团队规范文档）
└── assets/           # 可选：产出要用的模板 / 静态资源（如组件模板）
```

### SKILL.md 的两个部分

#### YAML 元数据头

// Agent 判定"要不要用这个 Skill"的唯一依据，只有两个字段：

```yaml
---
name: vue3-sfc-generator
description: 按团队规范生成 Vue 3 + TypeScript 单文件组件。当用户要求编写、生成、新建或补齐 Vue 组件时使用。不用于修改已有组件或非 Vue 项目。
---
```

- `name`：Skill 的名字
- `description`：**做什么 + 何时用**。这是入口守卫，写得好不好直接决定触发准不准

#### 正文（Markdown 指令）

// 只有 Skill 被触发后 Agent 才会读取正文。所以：

- "何时使用"信息必须全部写进 `description`，写进正文没用（正文在触发前根本不会被读）
- 正文只写"触发后怎么执行"：核心规则、工作流、审查规范、交付格式

### 渐进式披露：为什么 Skill 能省上下文

// 一个 Skill 的信息分三层加载，原理和前端的按需加载完全一致：

| 层      | 内容                                | 加载时机       | 前端类比                      |
| ------- | ----------------------------------- | -------------- | ----------------------------- |
| 第 1 层 | `name` + `description`（约 100 词） | 常驻上下文     | 路由表：永远在，用来匹配      |
| 第 2 层 | `SKILL.md` 正文（控制在 500 行内）  | 触发时才加载   | 页面代码：命中路由才拉取      |
| 第 3 层 | `scripts/` `references/` `assets/`  | 执行中按需读取 | 懒加载的 chunk：用到才 import |

这样即使挂了十几个 Skill，上下文也不会被撑爆——只有真正命中的那个才"展开"。

## eg: 写一个Skill（demo）

### 建目录

```bash
mkdir -p workspace/.user_skills/vue3-sfc-generator
```

Skill 必须放在 Agent 能够发现的技能目录下（不同环境路径不同，常见为 `workspace/.user_skills/<skill-name>/`），目录名就是 Skill 名。

### 写description设计触发条件

`生成 Vue 组件。` ------------> 用户问"Vue 是什么"也会误触发，这样命中就过宽了，
`生成带防抖的搜索框组件。` ------------> 换个组件就触发不了,这样命中又过窄了，

需写清楚做什么 + 何时用 + 不干什么：

```yaml
---
name: vue3-sfc-generator
description: 按团队规范生成 Vue 3 + TypeScript 单文件组件（SFC）。当用户要求编写、生成、新建或补齐一个 Vue 组件时使用，包括组件骨架、props/emits 设计、模板与样式。不用于修改已有组件或非 Vue 项目。
---
```

### 写正文

// 核心指令 + 工作流 + 审查规范，正文是触发后的"执行手册"，建议按四个板块组织：

1. 核心规则：不可妥协的硬约束（技术栈、命名、目录约定）
2. 工作流：从需求到产物的固定步骤（解析 → 设计 → 生成 → 自检）
3. 审查规范：交付前逐项自检的清单（可勾选、可验收）
4. 交付格式：产物长什么样、放在哪、怎么被使用

给Agent 的"自由度"要和任务的脆弱程度匹配：

- 组件骨架这种容易跑偏、一致性要求高的任务 → **低自由度**（具体到命名、结构）
- 文案、创意这类没有唯一答案的任务 → **高自由度**（给原则，不给模板）

### 完整示例

// `vue3-sfc-generator/SKILL.md`

```markdown
---
name: vue3-sfc-generator
description: 按团队规范生成 Vue 3 + TypeScript 单文件组件（SFC）。当用户要求编写、生成、新建或补齐一个 Vue 组件时使用，包括组件骨架、props/emits 设计、模板与样式。不用于修改已有组件或非 Vue 项目。
---

# Vue3 SFC 生成器

## 核心规则（必须全部遵守）

1. 使用 `<script setup lang="ts">` + Composition API
2. props 使用 camelCase，用 `defineProps` 声明并标注类型，禁止 `any`
3. 事件用 kebab-case 名称，通过 `defineEmits` 声明
4. 样式一律 `<style scoped>`
5. 组件放在 `src/components/<ComponentName>/`，并用 `index.ts` 统一导出

## 工作流

1. 解析用户需求，确定组件名（PascalCase）与用途
2. 设计 props / emits / slots；需求有歧义时先列出设计给用户确认
3. 生成 SFC 代码，严格遵循核心规则
4. 执行下方审查规范，发现问题先修正再交付

## 审查规范（交付前逐项自检）

- [ ] 类型完整：所有 props / emits 都有 TS 类型，无 any
- [ ] 命名规范：组件 PascalCase、props camelCase、事件 kebab-case
- [ ] 样式隔离：scoped，无全局样式泄漏
- [ ] 无冗余：无未使用的 import、变量、依赖
- [ ] 基础可访问性：交互元素有合理语义与键盘可达性

## 交付格式

- 输出完整 SFC 代码块，标注目标路径：`src/components/ComponentName/ComponentName.vue`
- 附 `index.ts` 导出代码
- 附一段最小使用示例，说明 props 与事件用法
```

### 最小闭环怎么跑通

此时我们已拥有一个最小可用 Skill了,蛋是，没有脚本、没有资源文件，只有一个 SKILL.md。他的闭环是：

```
用户一句话 → description 命中 → 读取 SKILL.md 正文
   → 按工作流执行 → 按审查规范自检 → 交付
```

## 让它真正"可用"：自测与调试

### 触发自测（正例 / 反例）

| 类型 | 输入                         | 期望   |
| ---- | ---------------------------- | ------ |
| 正例 | "帮我写一个分页组件"         | 触发   |
| 正例 | "生成一个表单校验组件"       | 触发   |
| 反例 | "帮我把现有组件的样式改一下" | 不触发 |
| 反例 | "Vue 和 React 的区别？"      | 不触发 |

### 输出校验

把生成结果瞅一下，看看是否符合要求

### 常见翻车点

| 问题             | 症状                       | 修法                               |
| ---------------- | -------------------------- | ---------------------------------- |
| description 过宽 | 不相关的请求也触发         | 收紧措辞，明确"不用于……"           |
| 正文含糊         | 产出不稳定、没法验收       | 把形容词改成可检查的硬规则         |
| 没有审查规范     | 交付前不自检，质量波动     | 补一个可勾选的 checklist           |
| 正文膨胀         | Skill 一加载就占大量上下文 | 细节拆到 references/，正文只留流程 |

## 进阶：渐进式披露与资源分包

当 `SKILL.md` 接近 500 行，或出现下面的信号，就该拆资源了：

| 出现的信号                                 | 拆到哪        | 前端类比               |
| ------------------------------------------ | ------------- | ---------------------- |
| 同一段代码每次都要重写（如生成组件的脚本） | `scripts/`    | 把重复逻辑抽成工具函数 |
| 很长的团队规范文档（如"组件规范.md"）      | `references/` | 按需 import，不进主包  |
| 固定模板 / 初始文件（如 SFC 模板、脚手架） | `assets/`     | 脚手架模板             |

拆分原则：**SKILL.md 只留"核心流程 + 指向"，并写清楚"什么时候该读哪个文件"**；细节交给资源文件，按需加载。

Skill 没有一次写对的。正确姿势是：用真实任务跑几轮 → 发现哪里理解偏了 → 改 SKILL.md 或补资源 → 再跑。

## 模板

```markdown
---
name: your-skill-name
description: <做什么>。当用户<触发场景 1>、<触发场景 2>时使用。不用于<边界场景>。
---

# <Skill 名>

## 核心规则

1. <硬约束，可检查>

## 工作流

1. <解析输入，确定……>
2. <执行……>
3. <按审查规范自检>

## 审查规范

- [ ] <可验收的检查项>

## 交付格式

- <产物形态、放置路径、使用方式>
```

## 附：交付前自检

- [ ] 只有一个 `SKILL.md` 也能完整干活
- [ ] `description` 精准触发：正例全中、反例不误伤
- [ ] 正文指令是可执行的硬规则，不是形容词
- [ ] 有交付前自检的审查规范
- [ ] 在真实任务上完整跑通过至少一轮
