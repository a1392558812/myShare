# OffscreenCanvas+Worker

> 当在主线程进行canvas绘制时，当绘制一高频，同一时刻主线程还要处理输入、布局、样式和别的业务代码。粒子一多，`requestAnimationFrame` 的回调就开始排队，掉帧就出现了。`OffscreenCanvas`实现的是把这块画布的绘图上下文所有权交给了Worker，之后指令在 Worker 里拼，主线程只负责合成。但代价是 API 少了很多：没有 `document`、没有 `HTMLImageElement`、`requestAnimationFrame` 不一定有、字体是另一套环境。

---

## 卡顿分析

很多人对 canvas 性能的第一反应是"我画的东西太多了，得优化绘制 API"。方向对了一半，但对不上症状。一个 60Hz 的屏幕，每帧给你 16.7ms。这 16.7ms 里主线程要排队做完：输入事件回调、微任务、样式计算、布局、部分绘制、以及`requestAnimationFrame` 回调，绘图代码不是独占这 16.7ms 的，它只是队列里的一个任务。

// 在`rAF` 里一下事时，卡顿会成倍放大：

- 每帧用 JS 重新计算几万个粒子的位置，再逐个 `fillRect` / `arc`；
- 每帧 `new Path2D()`、`save()/restore()` 做几百次；
- 用了 `shadowBlur`、`ctx.filter = 'blur(...)'` 这类需要额外离屏模糊通道的效果；
- 每帧 `getImageData()` 或 `toDataURL()` —— 这两个是**同步回读**，直接把 GPU 侧的像素拉回 CPU，帧预算瞬间见底；
- 顺带还在这个回调里更新 Vue 的响应式数据，触发一次组件更新。

// 举个栗子：

```js
const freeze = () => {
  const deadline = performance.now() + 300;
  while (performance.now() < deadline) {
    /* 空转，模拟一次同步长任务 */
  }
};
```

当我们点击这个按钮，主线程渲染的canvas在这300ms里画面是完全定住的。因此下一帧的 `rAF` 回调根本没机会执行, 这里有个常被误解的点：Canvas 2D 的 `fill`、`drawImage` 调用本身大部分是异步交给合成器/GPU 的，JS 侧返回得很快。所以"canvas 慢"往往不是绘制慢，而是**在 JS里构造这批绘制指令的时间，以及那些同步回读，吃掉了主线程的预算**。这点很中药，因为它直接决定了优化方向：要么减少指令数量，要么把构造指令的活儿挪走。本篇我们讨论`OffscreenCanvas`方案

## OffscreenCanvas：换线程

```js
const canvas = document.querySelector("#stage");
const offscreen = canvas.transferControlToOffscreen();

const worker = new Worker(new URL("./render.worker.js", import.meta.url), {
  type: "module",
});

// OffscreenCanvas是可转移对象，放进去之后它的所有权从主线程搬到 Worker，是零拷贝的所有权移交，不是序列化。忘了写这个数组，会报错
worker.postMessage({ type: "init", canvas: offscreen }, [offscreen]);
```

跑起来之后，Worker 里画的东西会出现在页面上那个 `<canvas>` 里。主线程不需要再做任何事，也不用 `drawImage` 拷回来。这块 `<canvas>` 元素变成了一个"占位图"，只负责布局和合成。

// 注意：

- **`transferControlToOffscreen()` 一块画布只能调一次。** 第二次调报错。而且转移是单向的，没有 `transferFromOffscreen`，主线程拿不回这块画布的控制权。
- **转移之前不能调用过 `getContext()`。** 只要这个 `<canvas>` 已经进入过任何一种上下文模式（2d、webgl），`transferControlToOffscreen()` 同样抛报错。所以别在 `mounted` 里先 `getContext('2d')` 试一下"能不能画"，再决定要不要转移。
- **转移之后，主线程 `canvas.getContext()` 返回 `null`。** 想在主线程再叠一层 2D 图形、或者画个 debug 网格，做不到。要么在 Worker 里画完，要么用另一个 canvas / DOM 元素叠上去。
- 组件卸载后重新挂载，**不能复用那个已经转移过的 DOM 节点**。Vue 里切换渲染模式、或者 `keep-alive` 缓存了组件，再激活时那个 canvas 已经是"死"的，只能换一个新的 `<canvas>` 节点。这一点后面 demo 里会再提。

### 像素尺寸

这是最容易处错的敌方。以前在主线程里，习惯是CSS 定宽高、JS 设 `canvas.width = rect.width * dpr`。但换成离屏之后逻辑没变，但 **`.width` 这个属性现在只有Worker能拿到**

```js
surface.width = Math.round(width * dpr);
surface.height = Math.round(height * dpr);
ctx.setTransform(dpr, 0, 0, dpr, 0, 0);
```

如果只让 CSS 尺寸变大而没同步改 `surface.width`，占位符 canvas 会把一张小位图拉伸铺满 CSS 盒子，就是那种"字都糊了但尺寸看着没问题"的经典现象。反过来，把位图设成 4K 屏的 3 倍 DPR，像素量是平方级增长，40k 粒子的填充率会直接爆掉。所以我在 demo 里把 DPR 封顶在 2：视觉上几乎看不出差别，填充率省一半。

// 注意：

- **改 `width`/`height` 会重置这个上下文的全部状态**，`transform`、`fillStyle`、`globalCompositeOperation` 统统回到默认，所以 `resetSurface` 里设置完尺寸，必须重新 `setTransform`，否则下一次缩放你就会发现坐标系全乱了。
- **DPR 会变。** 窗口拖到另一块不同缩放比的显示器、或者用户按住 Ctrl 缩放浏览器，`devicePixelRatio` 就变了。`ResizeObserver` 不一定能覆盖这种变化（CSS 尺寸可能一点没动），要额外监听一下 `matchMedia` 的 `resolution` 变化，或者干脆每次 resize 都重读一遍 DPR 做对比。

## Worker里的canvas

拿到 `OffscreenCanvasRenderingContext2D` 之后，日常用的 `fillRect`、`arc`、`drawImage`、`createLinearGradient`、`setTransform` 都在。但它毕竟不是 DOM 环境，缺的东西很具体：

| 能力                                       | Worker 里        | 换什么写法                                                     |
| ------------------------------------------ | ---------------- | -------------------------------------------------------------- |
| `document` / `window`                      | 没有             | 该传的参数从主线程传过来                                       |
| `HTMLImageElement` / `new Image()`         | 没有             | `fetch(url).then(r => r.blob()).then(createImageBitmap)`       |
| `img.decode()`                             | 没有             | 用上面的 `createImageBitmap` 链                                |
| `devicePixelRatio`                         | 不可靠           | 主线程读好，随 `init` / `resize` 一起传                        |
| `toDataURL()`                              | 没有             | `offscreen.convertToBlob({ type: 'image/png' })`，返回 Promise |
| `getImageData()`                           | **有**，但同样慢 | 能用，但别放进每帧循环                                         |
| `drawFocusIfNeeded` / `scrollPathIntoView` | 没有             | 这些本来就和 DOM 焦点、滚动相关                                |
| 字体 / `measureText`                       | 是另一套字体环境 | 用 `FontFace` 在 Worker 里注册，或主线程先量好把布局结果传过去 |

图片改用 `createImageBitmap`。主线程能 `createImageBitmap`，Worker 也能，而且 Worker 里做这件事更合适解码、降采样这些 CPU事，

```js
const loadBitmap = (url, width, height) =>
  fetch(url)
    .then((response) => response.blob())
    .then((blob) =>
      createImageBitmap(blob, {
        resizeWidth: width,
        resizeHeight: height,
        resizeQuality: "medium",
      }),
    );
```

- `createImageBitmap` 的 `resize*` 选项顺带把"加载完再缩放到目标尺寸"这一步也省了，比自己 `drawImage` 缩放质量好、还快。
- 字体并不统一，这个很重要。主线程加载的 webfont，Worker 里不一定知道；同一个 `font: '16px MyFont'`，两边 `measureText` 出来的宽度可能不一致。如果要在Worker 里排版文字（比如图表轴标签），做法是在 Worker 里用 `FontFace` 自己注册一遍字体，或者退一步：主线程量好宽度、算好换行，把结果作为绘制指令传给 Worker。前一种更干净，后一种更省事
- 注意降级方案

```js
const schedule = (callback) =>
  typeof self.requestAnimationFrame === "function"
    ? self.requestAnimationFrame(callback)
    : setTimeout(() => callback(performance.now()), 16);
```

## 数据处理

// 一种常见的错误用法是这么干的：Worker 算完一帧像素，`postMessage` 一整个`ImageData`回主线程，主线程再`putImageData`到可见canvas上。这等于把刚搬走的活儿又搬回来一半，而且每帧几 MB 的结构化克隆能把 GC 拖崩。

主线只有一条原则：**Worker 自己持有 `OffscreenCanvas`，自己出图，不需要回传像素。** 主线程只往 Worker 发参数：指针位置、尺寸、参数、命令。如果确实有大批量数据要双向流动（比如物理引擎在主线程、渲染在 Worker），再考虑下面这几种方案：

| 方案                                                  | 适用                                       | 代价                                                         |
| ----------------------------------------------------- | ------------------------------------------ | ------------------------------------------------------------ |
| 小对象 `postMessage`                                  | 指针、尺寸、配置、命令（本文 demo 走这条） | 每帧一两个消息，开销可忽略                                   |
| Transferable 双缓冲（`Float32Array` + transfer list） | 每帧几万个数值，双方都要读写               | 所有权移交后对方才能用，必须 ping-pong 两块 buffer 轮换      |
| `SharedArrayBuffer` + `Atomics`                       | 高频双向共享状态（多 Worker 协作）         | 需要站点开 COOP/COEP 响应头，否则 `SharedArrayBuffer` 不存在 |

绝大多数"canvas 卡顿"的案子停在第一行就够了。指针事件本身就 100Hz 左右，一个 `{x, y}` 的消息量远小于省下来的绘制时间。

### render.worker.js

Worker持有全部渲染状态。`getContext` 传 `alpha: false`（不透明画布，合成更快）和 `desynchronized: true`

```js
// src/render/render.worker.js
const TAU = Math.PI * 2;
const AXES = 2;

/*
rAF 在 Worker 里不是一定有，降级方案可做可不做，这里演示给一个，

但说句不好听的，用户浏览器都不兼容requestAnimationFrame，要么这个用户是个笨蛋，能忍受连requestAnimationFrame这个几乎标配api都没有的辣鸡浏览器。
要么这个用户电脑太拉，即便上了离屏方案它也拉

我的电脑是2017年的老古董，也能跑，
总之就是如果用户浏览器都不兼容requestAnimationFrame,那么“requestAnimationFrame降级方案”是我们会遇到的最小问题，后面他的浏览器铁一堆兼容毛病，放生他吧
*/
const schedule = (callback) =>
  typeof self.requestAnimationFrame === "function"
    ? self.requestAnimationFrame(callback)
    : setTimeout(() => callback(performance.now()), 16);

let surface = null;
let ctx = null;
let viewport = { width: 0, height: 0, dpr: 1 };
let scene = null;
let running = false;
let pointer = { x: 0, y: 0, active: false };
let frames = 0;
let sampleAt = 0;

const createScene = (count) => {
  const position = new Float32Array(count * AXES);
  const velocity = new Float32Array(count * AXES);
  let i = 0;

  while (i < count) {
    const index = i * AXES;
    const angle = Math.random() * TAU;
    const speed = 0.35 + Math.random() * 1.25;

    position[index] = Math.random() * viewport.width;
    position[index + 1] = Math.random() * viewport.height;
    velocity[index] = Math.cos(angle) * speed;
    velocity[index + 1] = Math.sin(angle) * speed;

    i += 1;
  }

  return { count, position, velocity };
};

const resetSurface = ({ width, height, dpr }) => {
  viewport = { width, height, dpr };

  // 像素尺寸只有这里能改，而且必须是 CSS 尺寸 × DPR
  surface.width = Math.round(width * dpr);
  surface.height = Math.round(height * dpr);

  // 改 width/height 会把绘图状态全部重置，transform 必须重新设
  ctx.setTransform(dpr, 0, 0, dpr, 0, 0);
  ctx.globalCompositeOperation = "source-over";
  ctx.fillStyle = "#0a0c14";
  ctx.fillRect(0, 0, width, height);
};

const step = () => {
  const { width, height } = viewport;
  const { count, position, velocity } = scene;

  // 不给 clearRect，改用半透明覆盖，顺便留出拖尾
  ctx.globalCompositeOperation = "source-over";
  ctx.fillStyle = "rgba(10, 12, 20, 0.16)";
  ctx.fillRect(0, 0, width, height);

  // 加法混合 + 单路径多圆弧：比逐粒子 fill 快一个量级
  ctx.globalCompositeOperation = "lighter";
  ctx.beginPath();

  let i = 0;
  while (i < count) {
    const index = i * AXES;
    let x = position[index] + velocity[index];
    let y = position[index + 1] + velocity[index + 1];

    if (pointer.active) {
      const dx = pointer.x - x;
      const dy = pointer.y - y;
      const distance = dx * dx + dy * dy;

      // 只在近处施力，避免每帧对全部粒子做一次开方
      if (distance < 90000) {
        const pull = 0.9 / (distance + 160);
        velocity[index] += dx * pull;
        velocity[index + 1] += dy * pull;
      }
    }

    const speed = Math.sqrt(velocity[index] ** 2 + velocity[index + 1] ** 2);
    if (speed > 2.2) {
      velocity[index] *= 2.2 / speed;
      velocity[index + 1] *= 2.2 / speed;
    }

    // 环绕，而不是碰壁反弹：不会在角落里堆积
    if (x < 0) x += width;
    else if (x > width) x -= width;
    if (y < 0) y += height;
    else if (y > height) y -= height;

    position[index] = x;
    position[index + 1] = y;

    // 先 moveTo 再 arc，否则 path 会在粒子之间连出多余的直线
    ctx.moveTo(x + 1.2, y);
    ctx.arc(x, y, 1.2, 0, TAU);

    i += 1;
  }

  ctx.fillStyle = "rgba(126, 198, 255, 0.5)";
  ctx.fill();
  ctx.globalCompositeOperation = "source-over";
};

// 统计放在 Worker 里，主线程一个字都不用算
const reportStats = () => {
  frames += 1;
  const now = performance.now();
  const span = now - sampleAt;
  if (span < 500) return;

  self.postMessage({ type: "stats", fps: (frames * 1000) / span });
  frames = 0;
  sampleAt = now;
};

const loop = () => {
  if (!running) return;
  step();
  reportStats();
  schedule(loop);
};

self.onmessage = (event) => {
  const message = event.data;

  switch (message.type) {
    case "init": {
      surface = message.canvas;
      ctx = surface.getContext("2d", { alpha: false, desynchronized: true });
      resetSurface(message.viewport);
      scene = createScene(message.count);

      running = true;
      sampleAt = performance.now();
      schedule(loop);
      break;
    }

    case "resize": {
      // 暂停中也要能改尺寸，ctx 一直在
      resetSurface(message.viewport);
      break;
    }

    case "pointer": {
      pointer = {
        x: message.x,
        y: message.y,
        active: message.active !== false,
      };
      break;
    }

    case "count": {
      scene = createScene(message.count);
      break;
    }

    case "pause": {
      running = false;
      break;
    }

    case "resume": {
      if (running) break;
      running = true;
      frames = 0;
      sampleAt = performance.now();
      schedule(loop);
      break;
    }

    case "snapshot": {
      // convertToBlob 是 Worker 里唯一能"导出画面"的途径，返回 Promise
      surface.convertToBlob({ type: "image/png" }).then((blob) => {
        self.postMessage({ type: "snapshot", id: message.id, blob });
      });
      break;
    }

    case "stop": {
      running = false;
      self.close();
      break;
    }

    default:
      break;
  }
};
```

几个刻意的性能取舍，顺带解释一下：

- **单路径多圆弧**。6000 个粒子如果逐个 `beginPath()` + `fill()`，就是 6000 次状态切换和 6000 次光栅化提交。攒进一个 path 里 `fill()` 一次，绘制指令数直接掉一个档次。代价是同一路径只能有一种颜色——所以想要多色粒子就分两三桶，而不是每颗粒子一个 `fillStyle`。
- **不用 `shadowBlur`**。它看起来最像"发光粒子"，但每个粒子带一次模糊通道，粒子数一过千帧率就崩，换到 Worker 里也一样崩。发光效果用 `globalCompositeOperation = 'lighter'` 叠加更便宜。
- **统计在 Worker 里做**。主线程只接收 2Hz 的 fps 数字，避免"为了测性能反而搞出性能问题"。

### useOffscreenStage.js

把 canvas 生命周期、事件、Worker 通信收在一个组合式函数里。注意挂载点：`document.fonts.ready` 之后再去转移（如果场景里有文字，这一步是先决条件），以及卸载时**必须 `terminate()`**,Worker 不会因为组件销毁而自动退出。

```js
// src/render/useOffscreenStage.js
import { onBeforeUnmount, onMounted, ref, shallowRef } from "vue";

const WORKER_ENTRY = new URL("./render.worker.js", import.meta.url);

const readViewport = (canvas) => {
  const box = canvas.getBoundingClientRect();
  return {
    width: Math.max(1, Math.round(box.width)),
    height: Math.max(1, Math.round(box.height)),
    // 3 倍 DPR 的像素量是 2 倍的两倍多，收益全在填充率上
    dpr: Math.min(window.devicePixelRatio || 1, 2),
  };
};

export const useOffscreenStage = (canvasRef, options = {}) => {
  const { count = 6000 } = options;

  const fps = ref(0);
  const supported = ref(false);
  const running = ref(false);
  const worker = shallowRef(null);

  const pendings = new Map();
  const unbinds = [];
  let observer = null;

  const send = (message, transfer = []) => {
    const target = worker.value;
    if (!target) return;
    target.postMessage(message, transfer);
  };

  const handleMessage = (event) => {
    const data = event.data;

    if (data.type === "stats") {
      fps.value = Math.round(data.fps);
      return;
    }

    if (data.type === "snapshot") {
      const settle = pendings.get(data.id);
      if (!settle) return;
      pendings.delete(data.id);
      settle(data.blob);
    }
  };

  const mount = () => {
    const canvas = canvasRef.value;
    if (!canvas) return;

    if (typeof canvas.transferControlToOffscreen !== "function") {
      supported.value = false;
      return;
    }

    supported.value = true;

    // 只有一次机会，转移前不要碰 getContext()
    const offscreen = canvas.transferControlToOffscreen();
    const instance = new Worker(WORKER_ENTRY, { type: "module" });

    instance.onmessage = handleMessage;
    worker.value = instance;

    instance.postMessage(
      {
        type: "init",
        canvas: offscreen,
        viewport: readViewport(canvas),
        count,
      },
      [offscreen], // 少了这行会报错
    );
    running.value = true;

    observer = new ResizeObserver(() => {
      send({ type: "resize", viewport: readViewport(canvas) });
    });
    observer.observe(canvas);

    const onPointerMove = (event) => {
      const box = canvas.getBoundingClientRect();
      send({
        type: "pointer",
        x: event.clientX - box.left,
        y: event.clientY - box.top,
        active: true,
      });
    };
    const onPointerLeave = () => send({ type: "pointer", active: false });

    canvas.addEventListener("pointermove", onPointerMove);
    canvas.addEventListener("pointerleave", onPointerLeave);
    unbinds.push(
      () => canvas.removeEventListener("pointermove", onPointerMove),
      () => canvas.removeEventListener("pointerleave", onPointerLeave),
    );
  };

  const unmount = () => {
    if (observer) {
      observer.disconnect();
      observer = null;
    }

    unbinds.splice(0).forEach((unbind) => unbind());

    // 还没回来的 Promise 先落地，别留悬空引用
    pendings.forEach((settle) => settle(null));
    pendings.clear();

    if (worker.value) {
      worker.value.terminate();
      worker.value = null;
    }
    running.value = false;
  };

  const toggle = () => {
    running.value = !running.value;
    send({ type: running.value ? "resume" : "pause" });
  };

  const setCount = (nextCount) => send({ type: "count", count: nextCount });

  // 导出当前画面：Worker 里 convertToBlob，主线程拿 Blob
  const snapshot = () =>
    new Promise((resolve) => {
      const id = Math.random().toString(36).slice(2);
      pendings.set(id, resolve);
      send({ type: "snapshot", id });
    });

  // 字体就绪前不开机，避免 Worker 侧量出的文字宽度和主线程对不上
  const boot = () => document.fonts.ready.then(mount);

  onMounted(boot);
  onBeforeUnmount(unmount);

  return {
    fps,
    supported,
    running,
    toggle,
    setCount,
    snapshot,
    remount: () => {
      unmount();
      boot();
    },
  };
};
```

`remount` 之所以是"卸载再挂载"而不是"复用"：那块 canvas 已经 transfer 出去了，同一节点上没有第二次机会。真要重来，得让模板换一个新的 `<canvas>`（`v-if` + `:key` 重建），再调 `remount`。

### 5.4 `CanvasStage.vue`

```html
<template>
```

### 对照实验

想自己复现"没有 OffscreenCanvas 会怎样"，把 `step` 原封不动搬到主线程就行，只换驱动方式：

```js
const runOnMainThread = (canvas, viewport) => {
  const ctx = canvas.getContext("2d");
  canvas.width = viewport.width * viewport.dpr;
  canvas.height = viewport.height * viewport.dpr;
  ctx.setTransform(viewport.dpr, 0, 0, viewport.dpr, 0, 0);

  const tick = () => {
    drawTo(ctx, viewport); // 与 Worker 里的 step 逻辑一致
    requestAnimationFrame(tick);
  };
  requestAnimationFrame(tick);
};
```

然后点"卡住主线程 300ms"：主线程版本画面定格，Worker 版本继续跑。区别不在于谁画得快，而在于那一帧的驱动权在哪个线程手里

## 怎么证明它真的不卡了

**不要看平均 FPS。** 平均值会被骗得很惨：一秒里 55 帧、卡一下丢 3 帧，平均 FPS 还是 58，主观感受却是"顿了一下"。卡顿感来自**帧间隔的长尾**。所以我更愿意看 p95 帧间隔——把每帧的 `now - last` 存下来排序取 95 分位：

```js
const samples = [];
let last = performance.now();

const sample = () => {
  const now = performance.now();
  samples.push(now - last);
  last = now;
};

const p95 = () =>
  samples
    .slice()
    .sort((a, b) => a - b)
    .at(Math.floor(samples.length * 0.95));
```

p95 超过 33ms，就意味着"至少有 5% 的帧是肉眼可感的一顿"。这个指标比平均 FPS 诚实得多，也比我在这里贴一堆跑分数字诚实得多，你的场景、你的机器、你的浏览器都不一样，数字自己跑才有意义。配套的三件事：
// 验证方法

- DevTools Performance 面板，录 3~5 秒，看主线程轨道上 `requestAnimationFrame` 回调占了多少。切换 Worker 模式前后对比，主线程上的绘制任务应该基本消失，只剩合成和输入。
- 埋点看帧间隔。上面那个 `sample()` 在 Worker 里跑最准，因为主线程的记录本身就会被长任务污染。
- 做减法验证。把粒子数从 6000 拉到 40000，主线程版本会先崩；Worker 版本崩得晚一些但一样会崩——它不是无限的性能提升，只是把预算从"和输入共享"变成"独占"。

## 注意

1. **`InvalidStateError: Cannot transfer control from a canvas that has a rendering context`**：转移前调过 `getContext()`。检查组件初始化顺序，别在 `mounted` 里先探测上下文。
2. **`InvalidStateError: Cannot transfer control from a canvas for more than once`**：同一节点想转移第二次。切换模式 / 组件重挂载时必须换新的 DOM 节点。
3. **`DataCloneError: OffscreenCanvas object could not be cloned`**：`postMessage` 第二个参数漏了 transfer list。
4. **`canvas.getContext('2d') === null`**：转移完成后的正常现象，不是 bug。主线程要叠图层就另起一个 canvas。
5. **画面糊成一片**：只改了 CSS 尺寸，没同步 `surface.width/height`。占位符把小位图拉伸了。
6. **坐标系突然错位、字体变巨大**：改了 `surface.width/height` 后没重设 `setTransform`，绘图状态被重置了。
7. **DPR 变了之后又糊了**：跨屏拖动或浏览器缩放，`ResizeObserver` 不一定触发。额外监听 `matchMedia` 的 resolution 变化，命中后重新走一次 `resize` 流程。
8. **`requestAnimationFrame is not a function`**：Worker 里裸调了。包一层 `schedule` 降级到 `setTimeout`。
9. **图片加载报 `Image is not defined`**：Worker 没有 `HTMLImageElement`。改用 `fetch` + `createImageBitmap`。
10. **文字宽度和主线程对不上**：Worker 与文档是两套字体环境。用 `FontFace` 在 Worker 注册，或者主线程量好再传。
11. **切到后台/元素隐藏后动画"停"了，回来时时间跳变**：不可见时 `rAF` 被节流。用 `performance.now()` 差值算位移，别假设固定步长。
12. **`SharedArrayBuffer is not defined`**：只有配了 COOP/COEP 响应头的页面才有它。不然老老实实用 transferable 双缓冲。
13. **`Vue` 里每帧 `ref.value = xxx` 导致组件狂更新**：响应式状态只在需要看的时候更新（fps 2Hz 足够），粒子数据用 `Float32Array` + `shallowRef`，别塞进 `reactive`。
14. **路由切走再切回，canvas 全黑**：Worker 没 `terminate()` 也没重建，或者复用了已转移的节点。

## 什么时候不该用它

`OffscreenCanvas` 不是"canvas 性能开关"，它解决的是一个特定问题：**主线程的时间片不够分**。如果这个前提不成立，它的收益接近零，而复杂度是实打实增加的。

- 动画很简单的那种主线程瞬间绘制完成（比如绘制一个圆环），搬去 Worker 反而多出一次消息往返、还丢了直接操作 DOM 叠层的便利，
- 需要频繁 `getImageData` 做像素级处理（比如滤镜、取色器）。同步回读的开销在 Worker 里一样存在，只是不再阻塞输入。这种情况该用 WebGL 或 `WebCodecs`，不是换线程，
- 强依赖 DOM 交互（画布上叠 HTML 表单、要做命中测试、要读 CSS 变量）。Worker 里读不到这些，你得把交互逻辑留在主线程、渲染搬走，等于维护两套坐标系统

补充：这套方案的复杂度集中在状态归属上，即一旦渲染状态进了Worker，主线程就再也读不到"现在画到哪一帧、某个元素是什么颜色"了，所以适合它的场景通常有共同特征：渲染是"自洽的"，主线程只喂输入、不查询画面。做游戏、做数据大屏、做长驻动效，都符合；做一个需要主线程随时读写画面状态的编辑器，就不太符合。
