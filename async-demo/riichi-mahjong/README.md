## 1. 项目概述（设计首页）

### 1.1 是啥

玩家在本地与电脑 AI 进行一场标准日本麻将（立直麻将）对战：摸牌、取舍、防守、和牌，用记牌器看清局面，用算番结算每局得失，以 10000 点起跑，打完半庄（或东风）比点数定胜负。

### 1.2 游玩条件

| 项 | 定义 |
|---|---|
| 玩家 | 1 人（玩家） vs 电脑 AI（1 人） |
| 平台 | Web 端 |
| 输入 | 鼠标（点击手牌打牌、点击按钮吃碰杠和、点击牌河查看记牌器） |
| 联网 | 完全离线：构建产物为纯静态文件，无 CDN、无远程请求、无后端 |
| 单局时长 | 东风战约 8–12 分钟；半庄战约 15–25 分钟（AI 思考 0.6–1.6 秒） |
| 技术栈 | Vue 3 + TypeScript + Vite + Canvas 2D（纯前端） |

### 1.3 玩家承诺

最有辨识度的能动性：每次打牌都是一次「进攻 vs 防守」的选择,向听推进的诱惑与放铳的风险同牌而行；记牌器让每一张已见牌都成为可计算的信息，算番让每一次和牌都得到可复算的回报。

### 1.4 设计支柱

| 支柱 | 反例（必须被拒绝） |
|---|---|
| **信息可读**：牌河、剩余牌、役种进度都必须实时可查，玩家永远能回答"这张牌还剩几张" | 不做"隐藏信息导致玩家无法判断"的规则（如不做里宝牌、不做对手手牌的随机猜测引导） |
| **规则可复算**：和牌判定、符番、点数全部由独立领域层计算，同一规则同时驱动判定、算番、记牌器和 AI | 不做"展示一套、结算另一套"的软性规则（如模糊役种、估算点数） |
| **离线完整**：从配牌到终局，全部逻辑在本地运行 | 任何依赖网络的功能（排行榜、云存档、在线匹配）不进入范围 |
| **双人适配自洽**：吃碰杠、流局、罚符在两人对战下都有明确闭环定义 | 不做照搬四人规则却无法在两人场景自洽的机制（如四风连打的含混处理） |

### 1.5 核心动词

摸牌 · 打牌 · 吃 · 碰 · 杠 · 立直 · 和（荣和 / 自摸） · 查牌（记牌器）

### 1.6 循环机制

每巡：摸入一张 → 判断副露与和牌机会 → 打出一张 → 对手响应；打出的牌进入双方可读的牌河，牌河与副露共同改写剩余牌统计与役种进度，下一巡的选择建立在这些新信息之上；和牌后由算番模块给出可验证的点数结算，点数滚动更新双方的胜负天平。

### 1.7 范围与非目标

| 做（P0/P1） | 不做（P2 或明确非目标） |
|---|---|
| 玩家 vs AI 双人完整一局（东风/半庄可配置） | 联网对战、在线匹配 |
| 记牌器三项：已打牌、剩余牌、可凑役种（含进张提示）,宝牌（ドラ）系：表宝牌、里宝牌、杠宝牌 | emmmm |
| 结束算番：符·番·点数·支付分配·本场加点 | 牌谱回放、战绩云同步 |
| 吃·碰·明杠·暗杠·加杠·立直·一発 | 人和（役满，地域规则差异大） |
| 流局：九种九牌 / 四杠散 / 四风连打 / 荒牌罚符 / 双倍役满细分（大四喜/纯正九莲按役满计） | emmmm |
| AI 三档难度（简单 / 普通 / 困难） | 牌谱导入、自定义牌局编辑 |

## 2. 玩法走读

东一局，你是庄家（亲家），对手 AI 是闲家。双方各 10000 点。

配牌完成，你看到手里有 `白 白 中 中 123m 45p 678s 33p 8s`。牌山还剩几十张，AI 的 13 张牌扣在它手牌区。你摸起一张 `7p`——现在手牌 14 张，`45p 67p` 连成两面搭子，听 `3p / 8p` 还要再推一手。你点击 `8s` 打出，牌落在你的牌河最后一列；界面右侧记牌器同步刷新：`8s` 的"未确认剩余"从 4 变为 3。

AI 摸牌后沉默 0.8 秒，打出一张 `9m`。它的牌河已有 `1p 5s 9m 東`，副露区干净——它很可能在打门前清。你点开记牌器的「可凑役种」页：当前进度最高的是 **混一色（筒+字）**：筒子 6 张、字牌 4 张、万/索 3 张，距达成还差把万/索全部换掉；旁边一行小字提示 **小三元** 进度 2/3——白、中已有对子，只差摸到第三张白或中。你决定先按混一色走。

巡目到 12，你碰了 AI 打出的 `中`（副露亮出 `中 中 中`），牌河已见 20 张。记牌器「剩余牌」页显示：`白` 还剩 2 张、`發` 还剩 4 张——你意识到如果凑出白發刻子，就是大三元。但你手里只有 `白 白`，而 AI 明显在防守字牌，`發` 一张未现。你选择放弃大三元幻想，把 `9m` 打出，听 `3p / 8p`。

倒数第 5 巡，你自摸 `8p`。和牌！算番面板弹出：手牌分解 `123m 45p 678s 33p 88p`+白对+中刻？——结算明细逐项列出：**门前清自摸和 1 番 + 断幺九 1 番 + 一杯口 1 番**，共 3 番，符 30，子家自摸闲家付 1000、亲家付 2000。AI 点数从 10000 扣到 7000。庄家（你）和牌，连庄，本场数 +1。

> `core/` 下的算番（`yaku.js`）、点数（`score.js`）、流程（`game.js`）一律以 RULES.md 为规则真值。
> 本文件只保留索引、双人适配要点与验收摘要

### 3.1 双人适配要点

1. **上家即对手**：双方互为上家，互相可以吃对方舍牌；每巡只有一位响应者，无多家竞争。
2. **听牌罚符固定 3000 点** ——四人标准的 1000/2000/3000 三家分摊在双人局无语义。
3. **自摸只向对手一人收取**（基础点 × 2）。
4. **双家立直**后荒牌即流局，立直棒结转下局。
5. **风位轮转**：場风恒为東 / 南；庄家自风 = 場风，闲家自风 = 場风的下一风位（東→南→西→北）。役牌（自风）判定随此轮转。

### 3.2 本作简化项

| 项目 | 说明 |
|---|---|
| 里宝牌 | 只有立直家可见，与「信息可读」原则冲突 |
| 人和 | 是否役满的地域差异大，双人局概率极低 |
| 双倍役满 | 大四喜、纯正九莲按役满单倍计 |
| 赤宝牌 | 无赤五 |
| 食替禁止 / 送杠禁止 | 未实现 |
| 立直后暗杠 | 未实现，立直后一律只能摸打 |
| 包牌（パオ） | 责任支付未实现 |
| 途中流局不罚符 | 本作所有流局统一按听牌罚符结算 |
| 顺位点（马） | 不做，只比点数差 |

## 4. 算番与点数

```plaintext
基本点 = 符 × 2^(2 + 番数)
子家荣和 = 基本点 × 4 ｜ 亲家荣和 = 基本点 × 6 ｜ 自摸 = 基本点 × 2   （均进位到百位）
≥ 5 番 或 基本点 ≥ 2000 → 按档位封顶（满贯：子 8000 / 亲 12000 / 自摸 4000）
```

## 5. 记牌器

记牌器是三大核心功能之一，常驻右侧面板，三个 Tab：**已打牌 / 剩余牌 / 可凑役种**。所有数据来自同一个「可见牌统计器」（见 5.2），禁止各 Tab 各自统计。

> **牌面展示统一（全局规则）**：用 `TileFace` 渲染真实牌面图形（复用 Canvas 离屏牌面缓存）——包括记牌器（已打牌、剩余牌、役种缺口、听牌/进张、振听命中牌）、顶栏宝牌指示、操作区的吃/杠/立直方案、调试面板，**以及和牌结算页**（和了牌、手牌分解、宝牌指示牌）。数字角标表示「已见张数 / 未确认剩余」。役种缺口里没有具体牌的（如「任意字牌」「三四五万」）仍用中文标签；提示文案里需要提到牌时，由引擎用 `tiles`（牌种数组）单独传给界面画牌面，文字里不再拼 `tileText`。
>
> 例外：规则手册 `RULES.md` 是规则真值文档，牌谱沿用标准记法（`1m` / `東`），不受此约束。

### 5.1 双方已打牌

- 双方牌河按标准 6 列 × 6 行（最多 36 张）摆放，最后打出的牌位于牌河最末位置并高亮；
- 悬停/点击任意一张已打牌，显示「谁·第几巡·打出」的浮层；
- AI 的副露、杠区同样可见（暗杠 V1 默认亮出，保证剩余牌口径一致）；
- 已打牌与副露共同构成"已见牌"，实时供 5.2/5.3 使用。

### 5.2 剩余牌统计

**口径定义**（关键，必须与 UI 文案一致）：

```
已见牌 = 自己的手牌 + 双方副露（含杠） + 双方牌河
未确认剩余[tile] = 4 − 已见牌[tile]
```

- 未确认剩余 = 牌山（顺序未知）+ 对手手牌（不可见）中该牌的总剩余数，玩家无法区分二者，因此统一以"未确认剩余"展示；
- 牌堆视图：34 种牌 × 各自剩余数，按花色分组（万/筒/索/字），支持按剩余数升/降序排序；剩余 0 的牌置灰；
- 每次自摸、副露、杠、打牌后实时刷新；牌山方向指示（尾巡）同步显示。

### 5.3 可凑役种（役种进度分析）

对当前手牌（含副露）实时计算"还能凑成哪些役种"，是本项目最具辨识度的功能。用户例子中的"大三元、九莲宝灯"均属此分析。

**算法**（`core/progress.js`，纯函数，输入输出确定）：

```
输入：counts（手牌）、melds（副露）、menzen、visible.remaining、seatWind/roundWind、riichi
输出：{ yakuman[], normal[] }，每项含：
  - name / han / category（yakuman | normal）
  - status：ACHIEVED（当前牌形已成立）| PROGRESSING
  - have：已具备的硬性要素（已成刻子 / 顺子 / 张数…）
  - soft：可转化的搭子 / 对子（尚未成面）
  - score = clamp01((have + soft × 0.5) / need)：接近度，用于排序与进度条
  - missing：缺口清单 [{ tile, label, need, remaining }]
  - min：进入列表所需的最低要素数（压掉「理论可行但毫无希望」的项）
```

**关键口径 —— 搭子/对子必须计入（`soft`）**：只统计「已成面子」会让开局几乎什么都看不到。手牌的真实状态是搭子与对子，此时各役的 `have` 全是 0，列表只剩按张数算的断幺九和按状态算的门前清自摸和。把搭子/对子按**半个要素**折进接近度后，路线才会正常浮现：456m+456p+456s 各两张 → 三色同顺 `0/3 +2`、已有一对三元 → 役牌 `0/1 +1`、三个对子 → 对对和 `1/4 +3`。

**结构化口径**（每役一览，`have` / `soft`）：

| 役种 | have | soft |
|---|---|---|
| 大三元 / 大四喜 | 三元（风）刻子数 | 三元（风）对子数 |
| 小四喜 | 风刻子 + 风雀头 | 其余风对子数 |
| 四暗刻 / 三暗刻 | 暗刻数（手内 3 张 + 暗杠） | 门清对子数 |
| 国士无双 | 幺九覆盖种类数 + 对子 | — |
| 字一色 / 绿一色 / 混老头 / 清老头 | 字牌 / 绿牌 / 幺九 / 幺九数牌张数 | — |
| 九莲宝灯 | 单花色门清时与基础型 `1112345678999` 的契合数 | — |
| 清一色 / 混一色 | 最大花色（+ 字牌）张数 | — |
| 断幺九 | 非幺九张数 | — |
| 对对和 | 刻子数（含副露） | 对子数 |
| 三色同顺 | 该点数三种色已成顺子数 | 还差一张的色数 |
| 一气通贯 | 已有完整段数（123/456/789） | 两段成搭的段数 |
| 三色同刻 | 同点数三色刻子数 | 同点数三色对子数 |
| 一杯口 / 两杯口 | 完全重复顺子数 | 只差一张的重复顺子数 |
| 混全（纯全）带幺九 | 含幺九的面子 + 雀头 | 含幺九的搭子数 |
| 小三元 | 三元刻子数 | 三元对子数 |
| 役牌 | 三元 / 场风 / 自风刻子数 | 同类对子数 |
| 七对子 | 对子数 | — |
| 平和 | 已有顺子数 | 两面搭子数 |
| 立直 / 门前清自摸和 | 状态位（门清 / 已宣言） | — |

**展示规则**：

- `ACHIEVED` 条目置顶，其余按 `score` 降序（越接近越靠前）；同分时缺口越稀缺越靠前；
- 役满区与普通役区分开展示，避免役满被普通役淹没；
- 默认「役满 TOP 6 + 普通役 TOP 10」，底部「展开全部」按钮放全量；`min` 门槛把开局噪声（如仅 1 张幺九 → 清老头）挡在列表外；
- 每行：`役名（番） | have/need（+N搭） | 进度条 | 缺：白×1（剩2）發×1（剩4）`，进度条长度即 `score`；
- 缺口里的顺子类（三色同顺 / 一气通贯）按「该段还差几张」计数，不是一律说缺 3 张；
- 与 5.2 同源：所有张数来自同一个「可见牌统计器」，禁止各 Tab 各自统计。

### 5.4 听牌与进张

- **听牌提示**：当前手牌（含刚摸牌）所有能直接和牌的牌：`有效进张 = { tile | shanten(hand + tile) == 0 }`，逐张显示未确认剩余；
- **进张提示**：所有能让向听数 −1 的牌（`shanten(hand+tile) < shanten(hand)`），按牌分类列出；
- 与 5.3 联动：进张牌命中某役种缺口时，该役种进度条目高亮（"摸到 发 → 大三元 2/3 → 3/3"）。

## 6. AI 设计

### 6.1 分层与难度

AI 与玩家信息**完全对称**：只使用公开信息（双方牌河、副露、杠、自己的手牌），不使用牌山顺序与玩家手牌——记牌器可见的数据即 AI 可用的数据，避免作弊观感。难度分三档，决策优先级不同：

| 难度 | 决策核心 | 适用对象 |
|---|---|---|
| 简单 | 仅牌效率：最短向听推进 + 孤张优先 | 新手熟悉规则 |
| 普通 | 牌效率 + 基础役种规划 + 立直判断 | 默认难度 |
| 困难 | 上述全部 + 防守（危险牌识别、弃和）+ 精确听牌剩余评估 | 需要挑战的玩家 |

### 6.2 打牌决策

```
评估候选打牌（对每张手牌）：
1. 向听数（shanten）：打掉后向听数最低的牌优先（向听公式见 9.x 数据模型）
2. 搭子价值：完成面子后的剩余价值（两面 > 嵌张/边张 > 单骑 > 孤张）
3. 役种亲和：是否破坏当前规划的役（断幺/清一色/混一色/役牌对子）
4. 安全度：该牌对玩家的威胁（见 6.4），困难档强制过滤"危险牌"（除非向听为 0 且牌河已无更优解）
组合为加权评分，取最高分打出；同分时随机
```

- 简单档：只用 1 + 2；
- 普通档：1 + 2 + 3；
- 困难档：1 + 2 + 3 + 4。

### 6.3 副露与立直

| 动作 | 决策规则 |
|---|---|
| 吃/碰 | 仅在「有效缩短向听」且「不破坏已规划役种 / 门清计划」时执行；普通档对副露保守（默认不副露，除非向听 −1 且役种不受损）；困难档允许为了断幺/对对和主动副露 |
| 明杠 | 仅当杠后补牌有役种收益（三杠子/岭上开花可能）且放铳风险低时执行；默认不轻易明杠 |
| 暗杠 | 不改变听牌的前提下可杠（困难档评估三杠子/四杠子进度）；杠后必须重算听牌 |
| 立直 | 向听 = 0 且满足：剩余有效进张 ≥ 阈值（普通 ≥3、困难 ≥4）、巡目 ≤ 14、当前无振听风险、点数优势不需要保守时；立直棒押 1000 |

### 6.4 防守（困难档）

- **现物**：玩家牌河打过的牌 = 100% 安全；
- **筋（kabe）**：玩家打过 `4m`，则 `1m/7m` 安全度上升；按 147/258/369 筋推断玩家听的同筋；
- **字牌**：未现字牌有碰/荣风险，已打过的字牌安全；
- **副露威胁**：玩家副露 ≥2 组时视为高威胁（可能快听/役满），进入弃和模式（只打现物/安全字牌）；
- **振听规避**：AI 已打过的牌不荣和（符合规则），打牌时避免立直后被振听限制（困难档）。

### 7.1 布局（1920×1080 基准，等比缩放）

```
┌───────────────────────────────────────────────────────┐
│ 场况栏：东场·第1局·本场0｜场风·自风｜双方点数｜供托   │
├───────────────┬───────────────────────┬───────────────┤
│               │  AI 手牌（背面 13 张） │   记牌器面板  │
│   AI 副露/杠  │  AI 牌河（6×6）       │  ┌───────────┐ │
│               ├───────────────────────┤  │ Tab1 已打牌│ │
│               │  牌山（背面·尾巡侧）  │  │ Tab2 剩余牌│ │
│               ├───────────────────────┤  │ Tab3 可凑役│ │
│   玩家副露/杠 │  玩家牌河（6×6）      │  └───────────┘ │
│               │  玩家手牌（14 张·点击打牌）│   操作按钮区│
└───────────────┴───────────────────────┴───────────────┘
```

- 牌桌主体（牌、牌河、牌山、副露、杠、动画）由 **Canvas** 绘制；
- 记牌器面板、操作按钮、场况栏、结算弹窗由 **Vue DOM** 组件渲染（便于布局与无障碍）；
- 双方点数常驻场况栏，每次结算滚动动画（Canvas 或 DOM 均可，P0 用 DOM transition）。

**布局硬约束（踩过坑，勿改回）**：

- Canvas 必须**绝对定位**在 `.board` 舞台内（`.board { flex: 1; min-height: 180px }`），不能作为 `.table` 这个 flex 列的普通子项。
  `setupCanvas` 按父级可用高度等比缩放，canvas 一旦留在流内，就会被撑到与整列等高；而 flex item 的 `min-height: auto` 让它**无法被压缩**，于是把下面的**操作按钮区**顶出容器，被 `.main { overflow: hidden }` 整行裁掉 —— 表现为「荣和/碰/杠/吃/过/自摸」和「点击手牌打出」完全看不见也点不到。
- 操作区 `.acts`、听牌条 `.waitline` 一律 `flex: none` 且 `z-index` 高于 canvas；立直方案面板限高 `34vh` 内部滚动，不允许把牌桌挤成 0。
- 舞台高度会随「听牌条 / 立直方案 / 侧栏」的出现与消失而变，`useMahjong` 必须用 `ResizeObserver` 监听 `.board` 实时重算缩放，保证渲染尺寸与点击命中（`getBoundingClientRect` + 同一个 `scale`）始终一致。

### 7.3 结算界面（算番展示）

和牌后结算弹窗按此顺序展示（数据来自 `core/score.ts` 单次结算结果）：

1. 手牌分解（面子/雀头，杠单独标注）；
2. 役种明细：每个役种一行（名称 · 番数 · 是否门清）；合计番数与符数；
3. 档位判定与点数：荣和/自摸、亲/子、本场加点、立直棒；
4. 支付方向：谁付谁收、点数滚动动画；双方点数更新；
5. 连庄/轮庄提示，进入下一局或终局胜负页。

**结算页里的牌一律是牌面图形**：和了牌、手牌分解（每组的每张牌）、宝牌指示牌都用 `TileFace` 渲染，不出现 `123m` / `東東東` 这类记谱文本。分解数据由 `breakdownOf()` 以**结构化**形式给出（`{ kinds, tag, concealed }`），`concealed: false` 的组（副露）画成金色虚线框区分；雀头组带「雀头」小标签。七对子 = 7 组各 2 张，国士无双 = 13 种幺九（含重复那张）铺开 + 一行文字。

> **雀头（head）必须由分解一路带回**：`decompose()` 递归到底时要带着 `head` 一起 `push`，否则标准形的 `head` 会恒为 -1 / undefined —— 后果不只是结算页画出空白牌（`drawImage` 抛异常），**符计算也会少算役牌雀头 / 连风雀头的 +2 符**，单骑判定、小四喜、四暗刻单骑同样会错。守卫测试 `.tmp/riichi-head.mjs`。

### 7.4 调试面板（`~` 键 / 顶栏「调试」按钮）

复盘与测试用的作弊面板（`components/DebugPanel.vue` + `composables/useDebug.js` 单例），不影响正常游玩：

| 功能 | 说明 | 约束 |
|---|---|---|
| 透视 | 显示对手手牌（Canvas 直接翻面），顺带显示 AI 向听数与待牌 | 仅查看 |
| 改手牌 | **把牌库的牌直接拖到某一张手牌上**（或先点手牌再点牌库），1:1 置换（自己 / AI 都可以） | 立直后锁定；**副露（吃碰杠）与牌河里的牌不可改** |
| 指定下一张摸牌 | **把牌库的牌拖进「你 / AI」的格子**（或点一下牌库 = 给当前 Tab 的人排队下一张摸牌，一次性，摸到即清空） | 牌山/王牌里没有该牌时退回随机摸牌并提示 |

拖拽交互：拖起后原格子变淡、跟随一张牌面预览，可投放的位置（摸牌槽 / 命中的手牌）会亮起金框；拖到手牌区空白会提示「拖到某一张手牌上才能替换」而不是静默失败。

**牌数守恒（防第 5 张）的关键设计**：

- 换牌是**1:1 置换**：手牌出一张、牌山进一张，每种牌全区域总数恒为 4，结构上不可能出现第 5 张；
- 补给**只从牌山取**（`takeWallTile`），不碰王牌区 —— 那里有宝牌指示牌；换掉的牌压回牌山最前端（最后才会被摸到）；
- 每次改写后跑 `checkIntegrity()`（任一种 >4 张或总数 ≠136 即整体回滚）；
- 摸牌入口统一走 `drawTile()`，指定的牌直接从牌山/王牌里摘出，摸到即清空排队标记。

## 8. 技术架构

### 8.1 分层

```
┌─────────────────────────────────────────────────┐
│  Vue 3 组件层（DOM）                            │
│  场况栏 / 记牌器面板 / 操作按钮 / 结算弹窗 / 菜单 │
├─────────────────────────────────────────────────┤
│  Canvas 渲染层（render/）                       │
│  牌桌：手牌·牌河·牌山·副露·杠·动画·骰子        │
├─────────────────────────────────────────────────┤
│  状态层（Pinia store / tableStore）             │
│  单一数据源：GameState → 双向订阅渲染与 UI      │
├─────────────────────────────────────────────────┤
│  领域层（core/，纯 TypeScript，零 DOM 依赖）    │
│  tiles / wall / hand / yaku / score / shanten /│
│  tsumo / progress / game / ai / rng            │
└─────────────────────────────────────────────────┘
```

约束：`core/` 不得引用 Vue、Canvas、DOM、window——保证可被 Node/Vitest 直接单测，且与渲染层完全解耦。

### 8.2 Canvas 渲染方案

- Canvas 2D（`getContext('2d')`），设备像素比适配（`dpr × 逻辑分辨率`），桌面 60fps 为性能基准；
- **牌面预渲染缓存**：34 种牌面 + 牌背一次性绘制到离屏 Canvas，主循环只做 `drawImage`，避免每帧重新绘制牌面细节；
- **分层绘制**：静态层（桌面、牌河底色）→ 动态层（手牌/牌山/牌河）→ 特效层（动画、高亮），脏区域仅重绘变更层；
- 动画：`requestAnimationFrame` 驱动，补间采用 easing 函数（打牌 150ms、摸牌 100ms、结算滚动 400ms）；
- 牌张尺寸：桌牌 64×88px（逻辑），牌河牌 40×56px，随窗口等比缩放（基准 1920×1080）。

### 8.3 状态流（单向数据流）

```
玩家/AI 动作 → core/game.ts 校验并推进状态机 → 返回新 GameState
→ tableStore 更新 → Canvas 订阅重绘 + Vue 响应式更新 DOM
```

- 所有规则判定（含 AI 决策）都在 `core/` 完成，渲染层只读状态；
- 每巡结束产生 `RoundEvent[]`（摸牌/打牌/副露/和牌/点数变更等事件流），供结算展示与后续回放（P2）复用；

### 8.4 离线与运行

| 项 | 方案 |
|---|---|
| 构建 | Vite 5 打包为纯静态产物；全部 JS/CSS/字体内联或本地引入，零 CDN 引用 |
| 运行 | `npm run dev` 本地开发；`npm run build` 后产物可 `vite preview` 或任意静态服务器打开；**断网状态下功能完整**（验收时断网验证） |
| 持久化 | `localStorage`：设置（局制/难度/速度）、战绩（场次/胜负/总得失点） |
| 音频（P2） | WebAudio 合成简单音效（摸/打/和/碰），不引入音频文件，保证离线体积 |
| 随机 | 洗牌用可注入种子的 PRNG（Mulberry32），支持回放复现 |

## 9. 数据模型

```ts
// 牌：34 种 × 4 张
type Suit = 'm' | 'p' | 's' | 'z';          // 万 / 筒 / 索 / 字
interface Tile { id: number; suit: Suit; rank: 1 | 2 | 3 | 4 | 5 | 6 | 7 | 8 | 9; }
type TileCount = number[];                    // 长度 34，index = suit*9+rank-1

// 副露面子
type MentsuType = 'chi' | 'pon' | 'kan' | 'ankan';
interface Mentsu { type: MentsuType; tiles: Tile[]; from?: 'self' | 'opponent'; }

// 手牌
interface Hand {
  closed: Tile[];          // 门清部分
  open: Mentsu[];          // 副露（含杠）
  isMenzen(): boolean;     // open.length === 0
}

// 局状态（GameState 主结构）
interface GameState {
  wall: Tile[];            // 剩余牌山（含顺序）
  deadWall: Tile[];        // 王牌区（杠补牌）
  players: [PlayerState, PlayerState];
  round: { wind: 'east' | 'south'; number: number; honba: number; riichiBets: number; };
  turn: 0 | 1;             // 当前摸牌方
  phase: 'draw' | 'action' | 'response' | 'settlement' | 'flow-round' | 'end';
  events: RoundEvent[];
}

interface PlayerState {
  hand: Hand;
  river: Tile[];           // 牌河（顺序 = 打出顺序）
  discards: { tile: Tile; turnIndex: number }[];
  points: number;          // 初始 10000
  riichi: boolean;         // 立直标记（含立直棒）
  isDealer: boolean;
  seatWind: Suit;          // 自风
}

// 结算结果（core/score.ts 输出，结算界面直接消费）
interface ScoreResult {
  handBreakdown: string[];         // 面子/雀头分解
  yaku: { name: string; han: number; menzenOnly: boolean }[];
  totalHan: number; fu: number;    // 符（七对/国士特殊值）
  limit: 'normal' | 'mangan' | 'haneman' | 'baiman' | 'sanbaiman' | 'yakuman';
  basePoints: number;              // 基本点
  payments: { from: 0 | 1; to: 0 | 1; amount: number; reason: string }[];
  honbaAddition: number;
  riichiBets: number;
}
```

### 9.1 向听数公式（AI 与进张共用）

```
shanten(hand) = min(标准型, 七对, 国士)

标准型：8 − 2×面子数 − 面子候补数 − 雀头分
  雀头分 = 已有雀头 ? 1 : (有对子可作雀头候补 ? 1 : 0)
  面子候补 = 搭子/对子可组成的面子候选（同组不重复计数）
  超载修正：面子数+候补数 > 4 时按超出部分扣减
七对：6 − 对子数（含役牌对子特判，不与标准型混算）
国士：13 − 幺九种类数 − (已有幺九对子 ? 1 : 0)
```

- `shanten == 0` 即听牌；进张分析（5.4）与 AI 打牌评估（6.2）均调用同一实现。
